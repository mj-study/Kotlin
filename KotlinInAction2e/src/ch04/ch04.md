# 4장. 클래스, 객체, 인터페이스

## 한눈에 보기

이 장은 "Java의 클래스 모델을 Kotlin은 어디서, 왜 다르게 가져가는가?"에 답한다.

- 클래스와 메서드는 기본이 `final`이다. 상속을 허용하려면 `open`을 명시한다.
- 가시성의 기본값은 `public`이고, Java의 package-private은 없다. 대신 모듈 단위의 `internal`이 있다.
- 중첩 클래스는 기본적으로 바깥 클래스를 모른다(Java의 `static` nested). 알려면 `inner`를 붙인다.
- 생성자·프로퍼티 선언이 클래스 헤더에 합쳐지고, `data class`, `by`, `object`, `companion object`가 Java의 보일러플레이트와 싱글턴/정적 멤버 패턴을 대체한다.

## 핵심 개념

### 인터페이스와 상속

Kotlin은 `extends`/`implements` 구분 없이 `:` 하나로 쓴다. 인터페이스(interface)는 메서드 본문을 가질 수 있다(Java의 `default` 키워드가 필요 없다). 상태(backing field)는 가질 수 없다.

```kotlin
interface Clickable {
    fun click()
    fun showOff() = println("Clickable")
}

class Button : Clickable {
    override fun click() = println("clicked")
}

fun main() {
    Button().click()
    Button().showOff()
    // 출력:
    // clicked
    // Clickable
}
```

`override`는 **필수 키워드**다. Java의 `@Override`처럼 생략 가능한 애노테이션이 아니다.

두 인터페이스에 같은 시그니처의 기본 구현이 있으면, 구현 클래스가 반드시 `override`해서 충돌을 직접 해소해야 한다. 어느 쪽을 부를지는 `super<타입>`으로 지정한다.

```kotlin
interface Clickable { fun showOff() = println("Clickable") }
interface Focusable { fun showOff() = println("Focusable") }

class Button : Clickable, Focusable {
    override fun showOff() {
        super<Clickable>.showOff()
        super<Focusable>.showOff()
    }
}

fun main() {
    Button().showOff()
    // 출력:
    // Clickable
    // Focusable
}
```

> 💡 **눈높이 설명**
>
> Java도 이 경우 컴파일 에러를 내고 `Clickable.super.showOff()`로 해결한다. 차이는 문법뿐이다. Kotlin은 `super<Clickable>`처럼 타입 인자 자리에 부모를 적는다.

### 변경자: final, open, abstract, override

Kotlin 클래스와 멤버는 **기본이 `final`** 이다. 이유는 "상속을 위해 설계하지 않은 클래스를 누가 상속해서 깨뜨리는 일"을 막기 위해서다(취약한 기반 클래스 문제, fragile base class).

| 변경자 | 클래스에 붙이면 | 멤버에 붙이면 |
|---|---|---|
| `final` (기본) | 상속 불가 | 오버라이드 불가 |
| `open` | 상속 가능 | 오버라이드 가능 |
| `abstract` | 인스턴스화 불가, 상속 전제 | 구현 없음, 하위 클래스가 구현해야 함 |
| `override` | - | 상위 멤버 재정의. **그 자체로 open** |

```kotlin
open class Animal {
    open fun sound() = "..."
    fun name() = "animal"            // final
}

class Dog : Animal() {
    final override fun sound() = "woof"  // 여기서부터 오버라이드 금지
}

fun main() {
    println(Dog().sound())
    // 출력: woof
}
```

> 💡 **눈높이 설명**
>
> Java는 "기본 열림, 막으려면 `final`"이고 Kotlin은 정반대다. 그래서 Spring 같은 프레임워크에서 프록시 때문에 `open`이 필요한 클래스는 `kotlin-spring` 컴파일러 플러그인으로 자동 개방하는 경우가 많다. 이 부분은 이 장 범위를 넘는다.

### 가시성 변경자

| 변경자 | 클래스 멤버 | 최상위 선언 |
|---|---|---|
| `public` (기본) | 어디서나 | 어디서나 |
| `internal` | 같은 **모듈** 안 | 같은 모듈 안 |
| `protected` | 하위 클래스 | 사용 불가 |
| `private` | 같은 클래스 안 | 같은 **파일** 안 |

```kotlin
// File: Util.kt
private fun helper() = 42          // 이 파일에서만 보임
internal class Config(val key: String)  // 같은 모듈에서만 보임

fun main() {
    println(helper())
    // 출력: 42
}
```

> 💡 **눈높이 설명**
>
> - Java의 package-private(기본값)이 Kotlin에는 없다. 패키지는 가시성 단위가 아니라 이름 공간일 뿐이다.
> - Java의 `protected`는 같은 패키지에도 열려 있지만 Kotlin의 `protected`는 **하위 클래스에만** 열려 있다.
> - `internal`의 "모듈"은 함께 컴파일되는 소스 묶음(Gradle 서브프로젝트 하나 정도)이다.
> - 노출 규칙이 있다. `public` 함수의 시그니처에 `internal` 타입을 쓰면 컴파일 에러다.

### 내포 클래스와 내부 클래스

클래스 안에 클래스를 선언하면 기본은 **바깥 클래스 참조가 없는** 중첩 클래스(nested class)다. 바깥 인스턴스를 쓰려면 `inner`를 붙인 내부 클래스(inner class)로 만들고 `this@Outer`로 참조한다.

```kotlin
class Outer {
    private val x = 10

    class Nested {                       // Java의 static class
        fun hi() = "nested"
    }

    inner class Inner {                  // Java의 non-static inner class
        fun get() = this@Outer.x
    }
}

fun main() {
    println(Outer.Nested().hi())
    println(Outer().Inner().get())
    // 출력:
    // nested
    // 10
}
```

| | Java | Kotlin |
|---|---|---|
| 바깥 참조 없음 | `static class` | 아무것도 안 붙임 |
| 바깥 참조 있음 | 아무것도 안 붙임 | `inner class` |

> 💡 **눈높이 설명**
>
> Java는 "내부 클래스가 기본"이라 바깥 참조를 모르고 들고 다니다 메모리 누수가 생기기 쉽다. Kotlin은 반대로 정했다. 바깥을 쓰고 싶을 때만 `inner`로 의도를 드러낸다.

### 봉인된 클래스 (sealed class)

하위 타입의 종류를 **컴파일 시점에 고정**하는 클래스다. 하위 클래스는 같은 패키지·같은 모듈 안에서만 만들 수 있다. 덕분에 `when`에서 `else` 없이도 모든 경우를 검사(exhaustive)할 수 있다. `sealed interface`도 가능하다.

```kotlin
sealed interface Expr
class Num(val value: Int) : Expr
class Sum(val left: Expr, val right: Expr) : Expr

fun eval(e: Expr): Int = when (e) {
    is Num -> e.value
    is Sum -> eval(e.left) + eval(e.right)
}

fun main() {
    println(eval(Sum(Num(1), Sum(Num(2), Num(3)))))
    // 출력: 6
}
```

새 하위 클래스를 추가하면 `when`이 있는 곳마다 컴파일 에러가 나서 누락을 잡아 준다. Java 17의 `sealed` + `permits`와 목적이 같고, 문법은 `permits` 없이 간단하다.

### 주 생성자, 부 생성자, 초기화 블록

클래스 이름 옆 괄호가 **주 생성자(primary constructor)** 다. 파라미터 앞에 `val`/`var`를 붙이면 프로퍼티가 동시에 선언된다. 추가 초기화 로직은 `init` 블록에 쓴다.

```kotlin
class User(val name: String, var age: Int = 20) {
    init {
        require(name.isNotBlank()) { "name is blank" }
    }

    constructor(name: String, birthYear: Int, now: Int) :
        this(name, now - birthYear)         // 부 생성자는 주 생성자에 위임
}

fun main() {
    val u = User("kim")
    println("${u.name} ${u.age}")
    println(User("lee", 2000, 2026).age)
    // 출력:
    // kim 20
    // 26
}
```

- 상위 클래스 생성자 호출은 헤더에서 한다: `class Dog(name: String) : Animal(name)`. 인터페이스는 괄호가 없다.
- 부 생성자는 반드시 `this(...)` 또는 `super(...)`를 호출한다.
- 생성자를 막으려면 `class Util private constructor()`처럼 쓴다.

> 💡 **눈높이 설명**
>
> Java에서는 필드 선언 → 생성자 파라미터 → `this.x = x` 대입, 이렇게 세 번 쓰던 것을 한 줄로 합친 것이다. 디폴트 파라미터가 있으니 오버로드용 부 생성자는 대부분 필요 없고, Java 상호 운용이 필요할 때만 쓴다.

### 프로퍼티와 get/set

Kotlin의 프로퍼티(property)는 "필드 + 접근자(getter/setter)"를 한 묶음으로 선언한 것이다. 접근자를 직접 정의할 수 있고, 값을 저장하는 필드는 `field` 식별자로 가리킨다.

```kotlin
class Counter {
    var count: Int = 0
        private set                       // 외부에서는 읽기만 가능

    var label: String = ""
        set(value) {
            field = value.trim()          // field: 백킹 필드
        }

    val isZero: Boolean                   // 저장 필드 없음, 호출할 때마다 계산
        get() = count == 0

    fun inc() { count++ }
}

fun main() {
    val c = Counter().apply { label = "  hi  "; inc() }
    println("${c.label} ${c.count} ${c.isZero}")
    // 출력: hi 1 false
}
```

인터페이스에는 추상 프로퍼티를 선언할 수 있고, 구현 클래스가 필드나 커스텀 getter로 채운다.

> 💡 **눈높이 설명**
>
> `label = "x"`는 필드 대입처럼 보이지만 실제로는 setter 호출이다. setter 안에서 `label = value`라고 쓰면 자기 자신을 다시 호출해 무한 재귀가 되므로, 반드시 `field`를 써야 한다. Java 쪽에서는 `getCount()`, `setLabel()`로 보인다.

### 데이터 클래스 (data class)

`data`를 붙이면 컴파일러가 **주 생성자에 선언한 프로퍼티**를 기준으로 `equals`, `hashCode`, `toString`, `copy`, `componentN`을 만들어 준다.

```kotlin
data class Point(val x: Int, val y: Int)

fun main() {
    val p = Point(1, 2)
    println(p)
    println(p == Point(1, 2))
    println(p.copy(y = 9))
    val (a, b) = p
    println("$a $b")
    // 출력:
    // Point(x=1, y=2)
    // true
    // Point(x=1, y=9)
    // 1 2
}
```

- Java의 `record`와 비슷하지만, Kotlin의 `data class`는 `var`도 허용한다. 다만 `val`을 권장한다.
- `copy()`는 일부만 바꾼 새 객체를 만든다(불변 객체 갱신 패턴).
- 본문에 선언한 프로퍼티는 `equals` 등에 포함되지 않는다.

### 클래스 위임과 `by` 키워드

상속 대신 **구성(composition)** 을 쓰고 싶을 때, 인터페이스 메서드를 다른 객체에 전부 넘기는 코드를 `by`가 대신 생성해 준다.

```kotlin
interface Printer { fun print(msg: String) }

class ConsolePrinter : Printer {
    override fun print(msg: String) = println(msg)
}

class PrefixPrinter(private val inner: Printer) : Printer by inner {
    override fun print(msg: String) = inner.print("[LOG] $msg")  // 일부만 재정의
}

fun main() {
    PrefixPrinter(ConsolePrinter()).print("hello")
    // 출력: [LOG] hello
}
```

직접 `override`한 메서드가 있으면 그쪽이 우선하고, 나머지는 `inner`로 전달된다. 같은 `by` 키워드가 프로퍼티 위임(delegated property)에도 쓰이지만, 그건 이 장 범위를 벗어나므로 해당 주제를 다루는 장에서 본다.

> 💡 **눈높이 설명**
>
> Java에서 `LoggingList implements List`를 만들면 메서드 20개를 전부 `inner.xxx()`로 전달하는 코드를 손으로 쓰거나 `ForwardingList` 같은 걸 상속해야 한다. `by`는 그 전달 코드를 컴파일러가 생성하는 것이다. 이렇게 하면 `final` 기본값과도 잘 맞는다.

### 객체 선언 (`object`)

`object`는 **클래스 선언과 단일 인스턴스 생성을 한 번에** 한다. Java의 싱글턴 패턴 대체다. 생성자는 쓸 수 없고, 인터페이스를 구현할 수 있다.

```kotlin
object Registry {
    private val items = mutableListOf<String>()
    fun add(item: String) { items += item }
    fun size() = items.size
}

fun main() {
    Registry.add("a")
    Registry.add("b")
    println(Registry.size())
    // 출력: 2
}
```

`object : 타입 { ... }`로 쓰면 이름 없는 **객체 식(object expression)** 이 되어 Java의 익명 클래스를 대신한다. 이때는 호출할 때마다 새 인스턴스가 만들어진다.

### 동반 객체 (companion object)

Kotlin에는 `static` 키워드가 없다. 클래스 안에 `companion object`를 두면 `클래스명.멤버`로 호출하는 정적 멤버처럼 쓸 수 있다. 주로 **팩토리 메서드**와 상수에 쓴다.

```kotlin
class Account private constructor(val id: String) {
    companion object {
        const val PREFIX = "ACC-"
        fun create(seq: Int) = Account(PREFIX + seq)
    }
}

fun main() {
    println(Account.create(7).id)
    // 출력: ACC-7
}
```

- 동반 객체는 진짜 객체라서 인터페이스를 구현하거나 확장 함수를 붙일 수 있다.
- Java에서 진짜 `static` 메서드로 보이게 하려면 `@JvmStatic`을 붙인다. 안 붙이면 `Account.Companion.create(7)`로 불러야 한다.

> 💡 **눈높이 설명**
>
> 정적 멤버는 "객체가 아니라서 인터페이스도, 상속도 못 쓰는" Java의 예외 영역이었다. Kotlin은 그 자리를 객체로 채웠다. 그래서 `Account` 자체가 아니라 `Account.Companion`이라는 싱글턴 객체의 메서드를 부르는 것이다.

### 인라인 클래스 (value class)

값 하나를 감싸 **타입 안전성**을 얻되, 런타임에는 감싼 값 자체로 처리해 객체 생성 비용을 줄이는 클래스다. `@JvmInline value class`로 선언하고 주 생성자에 프로퍼티가 정확히 하나 있어야 한다.

```kotlin
@JvmInline
value class UserId(val raw: Long)

@JvmInline
value class OrderId(val raw: Long)

fun findUser(id: UserId) = "user-${id.raw}"

fun main() {
    println(findUser(UserId(5)))
    // findUser(OrderId(5))  // 컴파일 에러: 타입이 다름
    // 출력: user-5
}
```

> 💡 **눈높이 설명**
>
> `Long` 두 개를 받는 `transfer(from: Long, to: Long)`은 인자 순서를 바꿔도 컴파일됩니다. `UserId`/`OrderId`로 감싸면 컴파일러가 잡아 준다. Java라면 래퍼 객체를 만들어 힙 할당 비용을 내야 하지만, value class는 대부분 감싼 값으로 풀려서 그 비용이 없다. 제네릭 인자나 nullable로 쓰는 경우에는 박싱될 수 있다.

## Java와 비교

| 항목 | Java | Kotlin |
|---|---|---|
| 상속 기본값 | 열림 | 닫힘(`final`), `open`으로 개방 |
| 오버라이드 표기 | `@Override` (선택) | `override` (필수) |
| 인터페이스 기본 구현 | `default` 메서드 | 키워드 없이 본문 작성 |
| 기본 가시성 | package-private | `public` |
| 모듈 단위 가시성 | 없음(JPMS 제외) | `internal` |
| `protected` | 같은 패키지에도 공개 | 하위 클래스에만 공개 |
| 중첩 클래스 기본 | 내부 클래스(바깥 참조 O) | 중첩 클래스(바깥 참조 X) |
| 바깥 참조 표기 | `Outer.this` | `this@Outer` |
| 상속 제한 | `sealed` + `permits` | `sealed class/interface` |
| 생성자 | 클래스 본문 안 | 주 생성자는 헤더, 부 생성자는 `constructor` |
| 값 객체 보일러플레이트 | `record` / Lombok | `data class` |
| 싱글턴 | private 생성자 + `getInstance` | `object` |
| 정적 멤버 | `static` | `companion object` (`@JvmStatic`) |
| 위임 | 손으로 전달 메서드 작성 | `by` |

## 헷갈리기 쉬운 점

- **`open`을 빼먹고 상속하려 함**: Java 습관으로 `class Child : Parent()`를 쓰면 `Parent`가 `final`이라 에러가 난다. 메서드도 `open` 없이는 오버라이드할 수 없다.
- **`override`는 자동으로 open**: 오버라이드한 메서드는 그 아래 하위 클래스에서 또 오버라이드된다. 막으려면 `final override`다.
- **`protected`를 package처럼 기대함**: 같은 패키지의 다른 클래스에서는 접근할 수 없다.
- **`inner` 없이 바깥 멤버 접근**: 중첩 클래스에서 바깥의 프로퍼티를 쓰면 컴파일 에러다. 메모리 누수 걱정 없이 Java의 static nested처럼 동작한다.
- **`data class`의 범위**: 주 생성자 밖에 선언한 프로퍼티는 `equals`/`toString`/`copy`에 반영되지 않는다.
- **`object`와 `companion object` 혼동**: 최상위 `object`는 독립 싱글턴이고, `companion object`는 클래스에 속한 싱글턴이다. 이름을 안 붙이면 `Companion`이다.
- **setter 안에서 프로퍼티 이름으로 대입**: `field`를 써야 한다. 이름을 쓰면 무한 재귀다.
- **`value class`가 항상 박싱을 피한다고 착각**: 제네릭, nullable, 인터페이스 타입으로 쓰면 박싱이 일어날 수 있다.

## 스스로 점검

1. 같은 시그니처의 기본 구현을 가진 인터페이스 두 개를 한 클래스가 구현하면 어떻게 해야 하는가?

<details>
<summary>답</summary>

구현 클래스에서 해당 메서드를 반드시 `override`한다. 부모 구현을 쓰고 싶으면 `super<인터페이스명>.메서드()`로 지정해서 호출한다.

</details>

2. 중첩 클래스와 `inner` 클래스는 무엇이 다르고, 바깥 클래스 인스턴스는 어떻게 참조하는가?

<details>
<summary>답</summary>

중첩 클래스는 바깥 인스턴스에 대한 참조가 없고(Java의 `static` nested), `inner` 클래스는 참조를 가진다. 참조는 `this@Outer`로 쓴다.

</details>

3. `sealed` 클래스를 쓰면 `when`이 어떻게 편해지는가?

<details>
<summary>답</summary>

하위 타입이 컴파일 시점에 고정되므로 `when`을 식(expression)으로 쓸 때 `else` 없이 모든 경우를 검사할 수 있다. 하위 타입을 추가하면 처리 누락이 컴파일 에러로 드러난다.

</details>

4. `data class`가 자동으로 만들어 주는 것은 무엇이고, 어떤 프로퍼티가 대상인가?

<details>
<summary>답</summary>

`equals`, `hashCode`, `toString`, `copy`, `componentN`이다. 대상은 주 생성자에 선언한 프로퍼티뿐이다.

</details>

5. `class A(b: B) : B by b`에서 `A`가 `B`의 일부 메서드만 `override`하면 나머지는 어떻게 되는가?

<details>
<summary>답</summary>

직접 `override`한 메서드는 `A`의 구현이 쓰이고, 나머지는 컴파일러가 만든 전달 코드가 `b`에게 위임한다.

</details>

## 확인 필요

- `source.md`의 1번 항목 하위 "변경자에 따른 설명"은 `final`/`open`/`abstract`/`override` 표로 해석해 정리했다. 의도와 다르면 알려 주길 바란다.
- `source.md`의 12번 항목이 비어 있어 다루지 않았다.
- `sealed` 하위 클래스의 선언 위치 제약(같은 패키지·같은 모듈)과 인라인 클래스의 박싱 조건은 Kotlin 버전에 따라 세부가 다를 수 있으니 책의 해당 절과 대조가 필요하다.
- 동반 객체에 인터페이스 구현·확장 함수를 붙이는 예제는 본문에서 설명만 하고 코드로 싣지 않았다. 책에서 어떤 예로 다루는지 확인이 필요하다.
