# 7장. 널이 될 수 있는 값

## 한눈에 보기

이 장은 "Java에서 `NullPointerException`(NPE)으로 런타임에 터지던 문제를 Kotlin은 어떻게 컴파일 시점에 막는가?"에 답한다.

- Kotlin은 타입 자체에 널 가능성(nullability)을 담는다. `String`은 null 불가, `String?`은 null 가능이다.
- null 가능 타입의 값은 검사 없이 멤버에 접근할 수 없다. 대신 `?.`, `?:`, `as?`, `let`, `!!` 같은 도구로 안전하게 다룬다.
- 대부분의 null 검사 `if` 문은 이 연산자들로 한 줄로 줄어든다.
- Java 코드와 섞이는 경계에서는 컴파일러가 널 가능성을 알 수 없는 플랫폼 타입(platform type)이 생긴다. 여기가 NPE가 다시 새어 들어오는 지점이다.

## 핵심 개념

### null 가능 타입(`T?`)

타입 뒤에 `?`를 붙이면 null을 담을 수 있다. 붙이지 않으면 null을 대입하는 것 자체가 컴파일 오류다.

```kotlin
fun main() {
    val a: String = "kotlin"
    val b: String? = null
    // val c: String = null   // 컴파일 오류
    // println(b.length)      // 컴파일 오류: b가 null일 수 있음
    println(a.length)
    // 출력: 6
}
```

> 💡 **눈높이 설명**
>
> Java에서 `String`은 "문자열이거나 null"인 타입이라, 매개변수를 받을 때마다 null인지 의심해야 한다. Kotlin의 `String`은 "반드시 문자열"이라는 약속이고, null이 올 수 있는 경우만 `String?`로 따로 표시한다. 즉 null 검사의 책임을 컴파일러가 가져가서, `String`을 받는 함수 안에서는 null 검사를 아예 안 해도 된다.

### null 검사와 스마트 캐스트

`if (x != null)`로 검사하면 그 블록 안에서 `x`는 자동으로 non-null 타입으로 취급된다(스마트 캐스트는 이미 앞 장에서 다룸).

```kotlin
fun printLength(s: String?) {
    if (s != null) {
        println(s.length)   // 여기서 s는 String
    } else {
        println("null")
    }
}

fun main() {
    printLength("abc")
    printLength(null)
    // 출력:
    // 3
    // null
}
```

### 안전한 호출 연산자(`?.`)

수신 객체가 null이면 호출하지 않고 결과를 `null`로 돌려준다. 그래서 결과 타입은 항상 null 가능 타입이 된다. 체이닝하면 중간에 하나라도 null이면 전체가 null이다.

```kotlin
class Address(val city: String?)
class Person(val name: String, val address: Address?)

fun main() {
    val p1 = Person("민준", Address("서울"))
    val p2 = Person("철수", null)
    println(p1.address?.city?.length)
    println(p2.address?.city?.length)
    // 출력:
    // 2
    // null
}
```

**Java 비교:**

```java
// Java
Integer len = (p.getAddress() != null && p.getAddress().getCity() != null)
        ? p.getAddress().getCity().length() : null;
```

> 💡 **눈높이 설명**
>
> `Optional.map(...).map(...)` 체이닝과 느낌이 같다. 다만 `Optional`처럼 값을 감싸는 객체가 새로 생기지 않고, 그냥 `T?` 타입 값이 오가므로 런타임 비용이 없다.

### 엘비스 연산자(`?:`)

왼쪽이 null이면 오른쪽 값을 쓴다. Java의 `Optional.orElse` 또는 삼항 연산자 null 검사에 대응한다. 오른쪽에 `return`이나 `throw`를 둘 수 있어서 "null이면 빨리 빠져나가기"에 자주 쓴다.

```kotlin
fun cityLength(city: String?): Int {
    val c = city ?: return -1     // null이면 즉시 반환
    return c.length
}

fun main() {
    val name: String? = null
    println(name ?: "이름 없음")
    println(cityLength("서울"))
    println(cityLength(null))
    // 출력:
    // 이름 없음
    // 2
    // -1
}
```

### 안전한 캐스트(`as?`)

타입이 맞으면 변환하고, 안 맞으면 `ClassCastException` 대신 `null`을 반환한다. 보통 `?:`와 같이 쓴다.

```kotlin
fun toInt(x: Any): Int = (x as? Int) ?: 0

fun main() {
    println(toInt(42))
    println(toInt("문자열"))
    // 출력:
    // 42
    // 0
}
```

### 널 아님 단언(`!!`)

"이건 절대 null이 아니다"라고 컴파일러에게 선언한다. 실제로 null이면 즉시 예외(NPE)가 난다.

```kotlin
fun main() {
    val s: String? = "hello"
    println(s!!.length)
    val t: String? = null
    println(t!!.length)   // NullPointerException
    // 출력:
    // 5
    // (예외 발생)
}
```

> 💡 **눈높이 설명**
>
> `!!`는 Kotlin이 막아 준 NPE를 개발자가 일부러 다시 허용하는 구멍이다. 쓸 수밖에 없는 경우(프레임워크가 값을 주입해 주는 등)가 아니면 `?.`, `?:`, `let` 등으로 풀 수 있는지 먼저 본다. 코드 리뷰에서 `!!`가 보이면 이유를 물어야 하는 신호로 삼아도 좋다.

### `let` 함수

null 가능 값을 non-null일 때만 람다로 넘겨 처리한다. `?.let { }` 형태로 쓴다. 값을 한 번 변수로 빼서 `if`로 감싸는 코드를 줄여 준다.

```kotlin
fun sendEmail(address: String) = println("send to $address")

fun main() {
    val email: String? = "a@b.com"
    email?.let { sendEmail(it) }       // non-null일 때만 실행
    val none: String? = null
    none?.let { sendEmail(it) }        // 아무 일도 안 함
    // 출력: send to a@b.com
}
```

### 나중에 초기화하는 프로퍼티(`lateinit`)

non-null 프로퍼티를 생성자에서 못 채우는 경우(DI, 테스트의 `@BeforeEach` 등)에 쓴다. 초기화 전에 접근하면 예외가 난다. `var`에만, 그리고 기본 타입(`Int` 등)이 아닌 타입에만 쓸 수 있다.

```kotlin
class Service {
    lateinit var name: String

    fun init() { name = "service" }
    fun show() = println(name)
}

fun main() {
    val s = Service()
    s.init()
    s.show()
    // 출력: service
}
```

> 💡 **눈높이 설명**
>
> `lateinit`은 `String?`로 선언하고 매번 null 검사하는 불편을 피하는 대신, "초기화 순서는 내가 책임진다"는 약속을 컴파일러에게 하는 것이다. 약속을 어기면 컴파일 오류가 아니라 런타임 예외가 난다.

### null 가능 타입의 확장 함수

확장 함수의 수신 객체를 `T?`로 선언하면 null인 값에도 호출할 수 있고, 함수 안에서 null 처리를 한다. 표준 라이브러리의 `isNullOrEmpty()`, `isNullOrBlank()`가 이런 예다.

```kotlin
fun String?.orDash(): String = if (this == null || isBlank()) "-" else this

fun main() {
    val a: String? = null
    println(a.orDash())
    println("값".orDash())
    println(a.isNullOrEmpty())
    // 출력:
    // -
    // 값
    // true
}
```

### 타입 파라미터의 널 가능성

제네릭 `T`는 상한을 지정하지 않으면 `Any?`를 상한으로 갖는다. 즉 `T`에 `String?`이 들어올 수 있다. null을 금지하려면 `T : Any`로 제한한다.

```kotlin
fun <T> describe(x: T) = x?.toString() ?: "null"   // T는 null 가능
fun <T : Any> require1(x: T) = x.toString()        // T는 non-null만

fun main() {
    println(describe<String?>(null))
    println(require1("a"))
    // 출력:
    // null
    // a
}
```

> 💡 **눈높이 설명**
>
> Java에서 `<T>`는 사실상 "아무 참조 타입이나"라 null도 들어간다. Kotlin도 `<T>`는 마찬가지로 null 가능 타입까지 받는다는 점이 처음에는 직관과 다르다. non-null만 받고 싶다면 `T : Any`를 명시해야 한다.

### 자바와의 상호운용: 플랫폼 타입

Java 메서드가 돌려주는 타입은 Kotlin이 null 여부를 알 수 없어서 `String!`처럼 취급한다(코드에 직접 적을 수 없는 표기). 이 값은 `String`으로도 `String?`로도 다룰 수 있지만, null이 실제로 들어 있는 값을 `String`으로 다루면 런타임에 예외가 난다.

```kotlin
fun main() {
    val s = System.getProperty("not.exist.key")   // Java 메서드, 반환 타입 String!
    val safe: String? = s                         // 안전: null 허용으로 받음
    println(safe?.length)
    // 출력: null
}
```

Java 쪽 코드에 `@Nullable`/`@NotNull` 같은 널 가능성 애너테이션이 붙어 있으면 Kotlin이 그것을 읽어 `String?`/`String`으로 해석한다.

## Java와 비교

| 항목 | Java | Kotlin |
|---|---|---|
| null 허용 여부 | 모든 참조 타입이 null 가능 | `T`는 불가, `T?`만 가능 |
| NPE 발견 시점 | 주로 런타임 | 대부분 컴파일 시점 |
| 안전 접근 | `if` 중첩 / `Optional.map` | `?.` |
| 기본값 | `Optional.orElse` / 삼항 연산자 | `?:` |
| 안전한 캐스트 | `instanceof` 후 캐스트 | `as?` |
| null 아님 단언 | (해당 없음, NPE 그대로 발생) | `!!` |
| null일 때만 실행 | `ifPresent` / `if` | `?.let { }` |
| 지연 초기화 | 필드를 null로 두고 나중에 대입 | `lateinit var` |

## 헷갈리기 쉬운 점

- `a?.b`의 결과는 `b`의 타입이 non-null이더라도 항상 `T?`다. null일 때 `null`을 돌려줘야 하기 때문이다.
- `?.let { }`은 null이면 아무것도 실행하지 않는다. `else` 동작이 필요하면 `?:`를 뒤에 붙이거나 일반 `if`가 더 읽기 쉽다.
- `!!`는 "검사"가 아니라 "단언"이다. 컴파일 오류를 없애 주는 대신 NPE 책임을 개발자가 진다.
- `lateinit`은 null 안전을 보장하지 않는다. 초기화 전에 접근하면 예외가 난다.
- 제네릭 `T`는 기본적으로 null 가능이다. `T : Any`로 막아야 non-null이 된다.
- 플랫폼 타입 값은 컴파일러가 검사해 주지 않는다. Java 호출 결과는 가능하면 `String?`로 받아서 경계에서 처리한다.

## 스스로 점검

1. `String`과 `String?`의 차이는 무엇이고, 컴파일러는 어떤 코드를 막는가?

<details>
<summary>답 보기</summary>

`String`은 null을 담을 수 없고, `String?`은 담을 수 있다. null 가능 타입의 값에 `.length` 같은 멤버를 바로 호출하는 코드와 non-null 타입에 `null`을 대입하는 코드는 컴파일 오류가 난다.

</details>

2. `person.address?.city ?: "알 수 없음"`이 하는 일을 순서대로 설명해 보라.

<details>
<summary>답 보기</summary>

`address`가 null이면 `?.`가 호출을 건너뛰고 전체를 null로 만든다. `address`가 있으면 `city`를 가져온다. 이 결과가 null이면 `?:`가 `"알 수 없음"`을 대신 쓴다.

</details>

3. `as?`가 일반 캐스트 `as`보다 안전한 이유는?

<details>
<summary>답 보기</summary>

타입이 맞지 않을 때 `as`는 `ClassCastException`을 던지지만, `as?`는 `null`을 반환한다. 그래서 `?:`와 함께 기본값 처리를 할 수 있다.

</details>

4. `lateinit var`와 `String?` 프로퍼티 중 어떤 경우에 `lateinit`을 쓰는가? 위험은 무엇인가?

<details>
<summary>답 보기</summary>

생성 시점에는 값을 못 채우지만 사용하기 전에는 반드시 초기화된다고 확신할 때(DI, 테스트 준비 코드 등) 쓴다. 초기화 전에 접근하면 런타임 예외가 나는 것이 위험이다.

</details>

5. `fun <T> f(x: T)`에 null을 넘길 수 있는가? 막으려면 어떻게 해야 하는가?

<details>
<summary>답 보기</summary>

넘길 수 있다. `T`의 암묵적 상한이 `Any?`이기 때문이다. `fun <T : Any> f(x: T)`로 상한을 `Any`로 지정하면 막힌다.

</details>
